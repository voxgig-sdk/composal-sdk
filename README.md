# Composal SDK

Composal API client, generated from the OpenAPI spec.

Composal runs AI agents for engineering teams: always-on persistent agents with their own instructions, memory and triggers, and Verify, whose browser agents test real user journeys on pull-request previews and releases. Its HTTP API also covers app hosting and a container registry.

Learn more about Composal API at [composal.com](https://composal.com).

This is an unofficial SDK for the Composal public API, generated by Voxgig with [`@voxgig/sdkgen`](https://github.com/voxgig/sdkgen). It is not affiliated with, endorsed by, or sponsored by the upstream API provider.

Learn more about Voxgig SDKs at [voxgig.com/sdk](https://voxgig.com/sdk/).

Full documentation for this SDK: [https://voxgig-sdk.github.io/composal-sdk/](https://voxgig-sdk.github.io/composal-sdk/)

> TypeScript, Python, PHP, Golang, Ruby, Lua SDKs, a CLI with an interactive REPL, an MCP server for AI agents, and the Postman collections package — all generated from one OpenAPI spec by [@voxgig/sdkgen](https://github.com/voxgig/sdkgen).

## About Composal API

**Credentials.** Every call takes a Composal personal access token, passed as the
`apikey` option; the SDK sends it as `Authorization: Bearer ...`. The token acts as its user,
with that user's organization memberships and agent access. The base URL is
`https://api.composal.com`, and every path keeps its `/api/v1` prefix. The CLI and the MCP
server read the token from `COMPOSAL_APIKEY`.

**Organizations.** Most resources live in an organization, passed as `organization_id`. It takes
the organization's slug or its public id. Composal's definition names this parameter
`org_slug` on some routes; here it is `organization_id` everywhere.

```python
import os
from composal_sdk import ComposalSDK

client = ComposalSDK({"apikey": os.environ.get("COMPOSAL_APIKEY", "")})
org = os.environ.get("COMPOSAL_ORGANIZATION", "your-organization")

# The organization's persistent agents.
for agent in client.Agent().list({"organization_id": org}):
    print(agent.data_get().get("id"), agent.data_get().get("name"))

# Its Verify projects: the apps whose user journeys Verify tests.
for project in client.Project().list({"organization_id": org}):
    print(project.data_get().get("slug"), project.data_get().get("website_url"))
```

Sending work to an agent, in TypeScript:

```ts
import { ComposalSDK } from '@voxgig-sdk/composal-sdk'

const client = new ComposalSDK({ apikey: process.env.COMPOSAL_APIKEY ?? '' })
const organization_id = process.env.COMPOSAL_ORGANIZATION ?? 'your-organization'
const agent_id = process.env.COMPOSAL_AGENT_ID ?? 'YOUR_AGENT_ID'

const input = await client.AgentInput().create({
  organization_id,
  agent_id,
  conversation_id: 'main',
  text: 'Summarise the pull requests merged yesterday.',
})
console.log(input.data())
```

**Agents.** `Agent` create makes a persistent agent from a `name` and an optional
`configuration` (its `instructions`, model policy and work repositories); it starts as a draft
while its runtime is provisioned. `AgentInput` create sends it a message in a conversation
(`main` is the default one). Acceptance is not an answer: the reply arrives in the
conversation, which `Agent` load reads with `$action: 'conversation'`. Runs, threads, routines,
workflow triggers and the agent's settings each have their own resource (`AgentRun`,
`AgentThread`, `AgentRoutine`, `AgentWorkflowTrigger`, `AgentSetting`).

**Actions.** A verb on a record is an action, passed as `$action`: `VerificationProjectRun`
create with `$action: 'cancel'` cancels a run, `App` create with `$action: 'archive'` archives a
hosted app.

**Retries.** Composal asks for an `Idempotency-Key` header on many writes, so that a retried
request is not applied twice. Switch on the SDK's idempotency feature,
`feature: { idempotency: { active: true } }`, and it adds a key to each write, which its own
retries of that call reuse.

**Files.** Twelve calls can answer with a file rather than JSON: images, recordings, archives,
plain text and downloads, such as `Evidence` load with `$action: 'download'`. This generation
does not read a binary body, so those calls report an unreadable response. Six uploads take
multipart form data or JSON; the SDK sends JSON.

**Scope.** Composal's definition is generated from its application's routes and holds 2,008
operations, including internal services, payment and telemetry callbacks and admin routes.
This SDK covers the areas Composal's API reference lists: persistent agents and their
marketplace, Verify (projects, scenarios, runs, findings, browser runners), hosting (apps,
environments, services, deployments, domains, CDN and static sites), the container registry,
and the current user, tokens, organizations, members and invitations. Within those areas it
leaves out routes marked internal or deprecated (the `/clawder` paths, which `/spark` replaces),
routes that need a credential other than a personal access token, and the agent event stream,
whose replies the conversation also holds. That is 726 operations, as 216 resources.

**Not yet run with a token.** Every request was checked against the definition, not against
Composal.

## Entities, not endpoints

This SDK exposes the API as **216 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`, `patch`, `remove`):

```ts
const client = new ComposalSDK()
const items = await client.Agent().list({ organization_id: "example" })
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Offline unit testing

Every SDK ships a built-in **test mode** that swaps the HTTP transport for
an in-memory mock, so your unit tests run fully offline — no server, no
network, and no credentials:

### TypeScript

```ts
// The offline mock starts EMPTY — seed it with the records the test needs.
// Shape: { entity: { <entity-name>: { <id>: <record> } } }
const client = ComposalSDK.test({
  entity: {
    page_project_run: {
      test01: { id: 'test01' },
    },
  },
})
const pageprojectrun = await client.PageProjectRun().load({ id: 'test01', organization_id: 'example_organization_id', project_id: 'example_project_id' })
// pageprojectrun is the PageProjectRun entity; .data() reads its mock record
console.log(pageprojectrun.data())
```

### Python

```python
client = ComposalSDK.test()
pageprojectrun = client.PageProjectRun().load({"id": "test01", "organization_id": "example", "project_id": "example"})
print(pageprojectrun.data_get())
```

### PHP

```php
// Seed fixture data so offline calls resolve without a live server.
$client = ComposalSDK::test([
    "entity" => ["page_project_run" => ["test01" => ["id" => "test01"]]],
]);
$pageprojectrun = $client->PageProjectRun()->load(["id" => "test01", "organization_id" => "example", "project_id" => "example"]);
```

## Quickstart

### TypeScript

```ts
import { ComposalSDK } from '@voxgig-sdk/composal-sdk'

const client = new ComposalSDK({
  apikey: process.env.COMPOSAL_APIKEY,
})

// List all agents (returns AgentEntity[], one entity per record)
const agents = await client.Agent().list({ organization_id: "example" })
for (const agent of agents) {
  console.log(agent.data())
}

// Load a specific agent (returns the entity, an AgentEntity)
const agent = await client.Agent().load({
  organization_id: 'example_organization_id',
  id: 'example_id',
})
console.log(agent.data())
```

## Use it from an AI agent (MCP)

The generated MCP server exposes this SDK's list and load operations as
[MCP](https://modelcontextprotocol.io) tools that Claude, Cursor or Cline
can call directly. It only reads: create, update, patch and remove become tools when the SDK's model sets
`main: kit: target: 'go-mcp': tool: write: true`. Build and register it:

```bash
cd go-mcp && go build -o composal-mcp .
```

Then add it to your agent's MCP config (Claude Desktop, Cursor, etc.):

```json
{
  "mcpServers": {
    "composal": {
      "command": "/abs/path/to/composal-mcp"
    }
  }
}
```

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

| Feature | Purpose |
| --- | --- |
| **DebugFeature** | Debug capture |
| **IdempotencyFeature** | Idempotency |
| **MetricsFeature** | Metrics |
| **PagingFeature** | Paging |
| **RatelimitFeature** | Rate limiting |
| **RetryFeature** | Retry |
| **SecretsFeature** | Secrets |
| **TestFeature** | Test transport |
| **TimeoutFeature** | Timeout |

Pass custom features via the `extend` option at construction time.

## Customizing this SDK

This repository contains its own generator (`.sdk/`), so the SDK is
customizable without forking any upstream tool:

- **The model** (`.sdk/model/`) is what generation reads: the API's
  entities and operations, the targets, the features, and this project's
  own settings. It is written in [aontu](https://aontu.dev), a JSON-based
  specification language designed for building ontologies: easy to edit
  by hand, and files unify rather than override, so small declarations
  compose into one model. Regeneration re-reads it every time.
- **Templates** (`.sdk/tm/`) and **components** (`.sdk/src/cmp/`) are
  the two layers of generation, copied into this repo: templates are the
  literal per-language source, components generate the API-shaped parts.
- **Regeneration overwrites.** Each run rewrites every generated file from
  the model, the templates and the components, so an edit made to
  generated output is lost. Say what this project needs in its own model
  (`.sdk/model/project.aontu`), or extend a target with a component of its
  own in `.sdk/src/cmp/<target>/`, registered with `registerComponent`,
  which `voxgig-sdkgen doctor` reports as an addition rather than drift.
- **Customise in `.sdk`.** Edit the templates and components first. When
  they cannot express a change, write a feature of this project's own, or
  an entire custom target, in `.sdk/model/`, `.sdk/tm/` and
  `.sdk/src/cmp/`, and add it by name (`voxgig-sdkgen feature add`,
  `voxgig-sdkgen target add`). This repository regenerates `.sdk` in full
  (`main: kit: copies: 'overwrite'`): set it to `'merge'` before
  customising, so that an add merges toolchain updates into the edited
  copies.
